## Covered behavior

- Shared activity Output and mapping/condition source trees display actual emitted fields and types during an explicit test. Schema-only fields no longer hide actual fields. Repeating scalar previews show item count and values rather than only the first item.
- Source labels identify activity name (type). Earlier named outputs remain addressable; other branches are marked available only after completion. Browsing a branch does not provide execution synchronization.
- Opening a flow does not fetch historical samples. Flow/schema changes, flow switching and clearing a completed test discard preview values. Late responses cannot repopulate a newer test session. The explicit historical sample endpoint excludes production runs.
- Stop test is tested with active, paused-debug and waiting runs, repeated cancellation and failed/nonterminal cancellation responses. Terminal confirmation precedes preview cleanup; failures retain cancellation controls. Cancellation is cooperative and does not reverse already committed external side effects.
- Read-only schema impact checks report structural additions/removals/changes, directly referenced saved activities and newly broken source mappings. Permission tests reject cross-project access. Checks neither save proposed schemas nor create engine runs.
- HTML/Markdown process/project/package documentation resolves activity name (type), schema name/kind/root and connection name/kind, flags missing references and redacts credentials.
- The sample catalogue gate checks schema references, starter payload contracts and source mappings. Executable connection-free samples cover JSON/XML mapping, validation failures and JSON `zone:[2,5]` to XML `User/Score` elements 2 and 5. Existing imported/customized samples are not silently rewritten.
- Native broker matrices cover JSON, XML, text, map and bytes; keys/headers/properties; acknowledgements, retries/redelivery, explicit confirmation/rejection, missing confirmation, duplicate handling, expiry and listener lifecycle as applicable to each protocol. Java OpenWire/JMS interoperability is included in ActiveMQ tests.
- REST checks exercise RabbitMQ management publish/fetch/ack, ActiveMQ Jolokia publish/browse/removal and Kafka REST create/subscribe/poll/commit/close, including generated REST sample Sutras.
- Database checks exercise local PostgreSQL/MySQL and remote PostgreSQL/MySQL-compatible MariaDB, parameter binding, rollback, engine execution and configured TLS/property resolution. Temporary test databases are cleaned by their fixtures; application installations are not switched to remote storage.

## Environment and limits

- Windows, Node.js 22.23.2; local ActiveMQ Classic 6.3.2 with OpenJDK 21 and RabbitMQ 4.4.0. Installed local broker processes were started for testing without changing their configurations.
- Initial local REST attempts encountered connection refusals before broker listeners were ready. Those logs are retained as environmental failures; the explicitly identified clean retry passed all four checks. They are not silently counted as successes.
- Local secure broker checks use short-lived strict mutual-TLS proxies. They verify connector TLS trust/client-certificate behavior, not broker-native keystore configuration or public certificate issuance.
- Kafka SASL used verified TLS with the service CA. Kafka REST used HTTPS trust appropriate to its endpoint. The user explicitly authorized storing the Kafka key in an ignored local test folder. Git exclusion, restricted Windows file permissions and key/certificate correspondence were verified; credentials are not included in this report. An initial mutual-TLS run hit a 180-second file-level harness timeout after three passing scenarios. A 900-second retry passed all nine scenario assertions but timed out during teardown: nine passes, zero assertion failures, one file-level cancellation. A diagnostic rerun of listener restart/concurrency passed and exited cleanly in 73.92 seconds, including listener stop, publisher close, topic deletion and server stop. The full-run teardown stall was not reproduced or attributed to a runtime defect; it remains a limitation, not a clean full-suite exit. Exact temporary topics from the interrupted attempts were removed separately.
- The newly supplied remote PostgreSQL URI selects `postgres`, which passes engine/binding/rollback tests. A read-only attempt using the separately stated database name `sutraflow` returns an upstream connection failure. Client-to-pool TLS is encrypted and certificate-authorized; the pool's backend `pg_stat_ssl` report is not evidence of that client connection. Neither running installation is reconfigured to use this remote endpoint.
- Schema impact is advisory, scoped to saved drafts/direct references. It is not proof of regex/format/alternative-schema compatibility, deployed snapshot compatibility or transitive XSD dependency compatibility. Run representative payloads after a contract change.
- Linux/Docker verification, a prolonged remote-database soak, public ACME issuance and fresh SQL Server/Oracle live certification were not performed in this pass. Historical release evidence is not substituted for these gaps.

## Repeating the external Kafka matrix

With the broker endpoint, test opt-in and TLS/authentication environment variables configured, run the external matrix separately from the default regression gate:

```sh
node --import tsx --test --test-concurrency=1 --test-timeout=900000 test/kafka.test.ts
```

Use `SUTRA_KAFKA_CA_FILE`, `SUTRA_KAFKA_CLIENT_CERT_FILE` and `SUTRA_KAFKA_CLIENT_KEY_FILE` for private local PEM file paths, and `SUTRA_KAFKA_SASL=none` for client-certificate-only authentication. The default 180-second file budget is insufficient for the full hosted Kafka retry/listener matrix. Do not embed credentials in commands or commit PEM keys. Broker-specific service endpoints and CA chains must match the selected authentication method.
