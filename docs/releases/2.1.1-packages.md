Each archive's SHA-256 is in the `.sha256` file beside it (this receipt travels inside the archives, so it cannot hold their hashes). Check with `sha256sum -c <archive>.sha256`, or on Windows `Get-FileHash <archive> -Algorithm SHA256`.

Version 2.1.1, 268 files each. Each archive contains:
- the web installer and upgrader (`dist/server/install`, `dist/web/install.html`);
- `docs/install-example.json`;
- `.htaccess`, `web.config` and `install-sutraflow.html`.

There is no source, no tests, no soak tool and no development packages; the offline archive adds the runtime packages.

## Release gates

**Done on 26 and 27 October 2026, from these or earlier 2.1.1 builds of the same installer:**

- **Full test suite** on real PostgreSQL 18 (pgvector) and MySQL (Laragon): 537 tests, 526 passed, 0 failed, 11 skipped. The skipped tests need outside services: real brokers, MongoDB Atlas, Docker, and a remote database with TLS.
- **Web installer on PostgreSQL**, page by page in a browser, from the final build. Next was refused until the connection test passed. Test connection made the database and enabled pgvector 0.8.6, and the install made 52 tables. The administrator signs in and a wrong password is refused.
- **Web installer** (SQLite), page by page in a browser:
  - a busy port was found and a free one suggested;
  - the administrator signs in and a wrong password is refused;
  - the installer locks itself when it is done.
- **Silent install**:
  - on SQLite;
  - on PostgreSQL, with the database made by the installer and Node memory set;
  - a cluster engine started from its generated settings file joined the cluster.
- **Upgrade from 2.1.0**, with data and a deployed Sutra:
  - on SQLite (twice) and on PostgreSQL;
  - the PostgreSQL dump was read back before anything changed;
  - the data compared unchanged, and the Sutra from before still runs.
- **Rollback**: an upgrade to a deliberately broken build failed at start, put 2.1.0 back with its database, and started it.
- **Node memory** was set at install and changed in Tuning. Restart from the Admin Console then applied the new limit, both for the studio and for a cluster engine in another folder.
- **Web root**: the Windows archive was unpacked into Laragon's `www` with a stand-in `sutraflow.env` and key.
  - Apache 2.4 served the install page for the folder.
  - It returned 403 for everything else: `sutraflow.env`, the data folder, `bin`, `dist`, `docs` and the `.htaccess` itself.
- **Final archive**: `install --config --dry-run` printed the plan, and `help` lists `install`, `upgrade` and `setup`.
- **Runtime check** (`tools/runtime-check.mjs`) of the Linux archive, run on Windows: install, Node memory, Restart, and an upgrade from the 2.1.0 Linux archive.
- **Connections in the browser**: in a fresh studio, each kind was set up in its form, tested with Test connection, and saved. All passed:
  - HTTP to a public HTTPS API;
  - PostgreSQL local and remote (TLS);
  - MySQL local and remote;
  - Kafka with TLS and SCRAM-SHA-256;
  - local RabbitMQ and ActiveMQ (AMQP 1.0);
  - MongoDB Atlas by URI secret.

  Remote settings came from Project properties and Secret properties, so no password was typed. The pictures are in the user guide under *Connection examples*.
- **Ten-minute soak** on local PostgreSQL: 25 checks passed.
- **New soak trials** (Amaron shop, local RabbitMQ and ActiveMQ, Kafka, MongoDB, remote databases, AI): every check passed after two fixes.
  - One fix was a real product bug: a JSON message body written as text was published as a quoted string.
  - The other was a check in the soak itself, and was corrected.

## Deployment

Not yet deployed. 4800 (source folder) and 4810 (Laragon) still run 2.1.0. To deploy 2.1.1 to either one, run `bin\sutraflow.cmd upgrade` from the unpacked 2.1.1 folder, pointed at that installation.
- 4810 keeps its own `.htaccess` with the proxy note.
- 4800 runs from the source folder, so it is upgraded by building there instead.
