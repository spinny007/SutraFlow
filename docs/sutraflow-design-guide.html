Foundations

1. About this guide

This guide sets the standards for designing Sutras: how to structure a project, name things, build functions and transformations, expose APIs and web services, connect systems, design microservices, handle errors and release safely. The SutraFlow User Guide says what each activity and screen does; this guide says how to put them together so that the result is correct, secure, fast and easy for the next person to look after.

ReaderUse this guide to
DesignersShape a Sutra before building it; settle names, contracts and error paths early.
Reviewers and leadsReview a Sutra or project against the rules and the checklist (Design review checklist).
ArchitectsDecide service boundaries, integration patterns and how systems talk to each other.
AdministratorsKnow what designers were asked to do, so production settings fit (the Administration Guide covers the servers).

How the rules are written

WordMeaning
MustRequired. A Sutra that breaks it does not pass review, unless the reason is written in the Sutra's description.
ShouldExpected. Break it only for a reason you can explain.
MayAllowed; use your judgement.

Examples use an order business (orders, customers, stock, invoices) because it is easy to picture; the rules are the same for any domain. Activity names link to the activity reference in the user guide.

Where to start

New to SutraFlow: read How a Sutra runs and Designing Sutras: patterns and good practice in the user guide first, then Design principles here.

2. Design principles

Twelve principles sit under every rule in this guide. When a rule does not cover a case, decide by these.

#PrincipleIn practice
1One purpose per SutraA Sutra does one business thing (Accept an order, Send the invoice). Ten to thirty steps; more means it should be split into called Sutras.
2Contracts firstAgree the input and output (a JSON Schema, XSD or WSDL) before building. Every entry point and every called Sutra has one.
3Validate at the doorBad input is refused where it enters, with a clear answer, never deep inside the Sutra.
4Safe to repeatSteps that change things can run twice without harm: retries, redeliveries and recovery after an engine stops all repeat work.
5Fail visiblyEvery failure ends somewhere a person or a system sees it: an error reply, an alert, a dead-letter queue, a logged run. Nothing is swallowed.
6Configuration outside the designAddresses, names, limits and secrets that differ per environment live in properties, connections and the vault, never in steps.
7Reuse, do not copyShared logic is a called Sutra; shared connections and schemas are project resources.
8Carry references, not contentLarge data stays in files, tables and storage; the run carries paths and ids.
9Push work downThe database sorts and joins, the data platform crunches; the Sutra orchestrates and checks.
10Least rights, both waysEvery entry point has a policy; every connection signs in with its own account with only the rights it needs.
11Observable by designSteps named and described, business keys logged, step data kept as the Sutra's sensitivity allows.
12Rules decide, people approve, AI assistsBusiness rules are ordinary steps; decisions with risk go to a person; AI classifies, extracts and drafts.

3. Projects, folders and naming

Names are read far more often than they are written: in mappings ({nodes.Find the customer.rows}), logs, run history, alerts, the generated documentation and the Admin Console. A good name says what the thing is or does, in the words of the business.

Projects and folders

  • Must: one project per business domain or bounded context (Orders, Billing, Customer care), not per person or per technology. A project is the unit of release, properties and connections.
  • Should: folders inside a project by business capability: Orders/Intake, Orders/Fulfilment, Orders/Reports. Shared called Sutras in Shared (or Lib); test helpers in Test.
  • Should: resources (connections, policies, knowledge bases, memory tables) in Resources folders named after the system they reach: Resources/ERP, Resources/Payments.
  • Must not: copy a Sutra to change it a little. Make the difference a property or an input of a called Sutra.

Descriptions

  • Must: every Sutra has a description: what it does, what starts it, what it changes, who owns it.
  • Should: every step has a description (General tab) that says why it is there, not what its type is: Customers may only see their own orders: filter by the token subject.
  • Descriptions flow into the generated documentation (Documenting Sutras), so a well-described project documents itself.

4. Anatomy of a Sutra

Most Sutras follow the same shape. Using it everywhere means anyone can open a Sutra and find their way.

StageWhat happensTypical activities
1. ReceiveThe trigger starts the run with the request, message, file or event.REST service, SOAP service, Queue / topic trigger, File trigger, Timer, Channel trigger
2. ValidateRefuse what is wrong, with a clear reason.Body schema on the trigger, Validate fields, If / else
3. EnrichLook up what the work needs.SQL query, Send HTTP request, Get Memory Record, Call Sutra
4. TransformShape the data for the target.Map data, Map JSON Data, Map XML Data, Transform (JSONata)
5. ActChange something: write, send, publish.SQL update, SQL transaction, Publish message, Write file, Send HTTP request
6. ReplyAnswer the caller, as early as possible.Send HTTP response, SOAP reply, Return, Confirm message
7. RecordA business milestone in the log.Log
Error pathWhat happens when a step fails.Error outputs, Error handler, Throw error, End

Rules

  • Must: a Sutra with a caller waiting (REST, SOAP, MCP, a called Sutra with Wait) reaches its reply on every path, including errors. A path without a reply makes the caller wait until Reply wait runs out (504).
  • Should: lay the canvas out left to right in the order above, the happy path on one line and error paths below it.
  • Should: connect the error output of every step that talks to another system, or rely on an Error handler that handles every failure the same way (see Error handling).
  • Should: end branches that are finished with End where it makes the intent clear (stop this branch, or end the run with a status).
  • May: mark a step still to be designed with No operation; it must be gone before release.

Durable or in memory

Durable (default)In memory
SavedEvery step; a run survives a restart and continues on another engineOnly the finished run
SpeedGoodSeveral times faster for short Sutras
Waits, approvals, long workYesNo: steps cannot wait
Use forAnything that changes data, waits, or must not be lostShort request and reply lookups that can be repeated by the caller

Should: choose in memory (Sutra tuning, Execution) only for read-only or repeatable request and reply Sutras of a few steps. When in doubt, durable.

5. Functions and transformations in detail

Most of a Sutra's logic is data work: picking fields, reshaping documents, calculating, formatting. SutraFlow gives several ways to do it. Choosing the right one keeps Sutras readable and fast.

Choose the tool

NeedUseWhy
Build a document field by field, with repeating linesMap data, Map JSON Data (typed JSON), Map XML Data (XML with namespaces and attributes)Visual, checked against schemas, documented automatically
A value in a setting (a file name, a message)An = formula or {{ }} reference in the fieldNo extra step
Group, pivot or query a whole JSON documentTransform (JSONata)One expression does what many mapping rules would
Filter, sort or total a listFilter list, Sort list, Aggregate, or a For-Each with Where and Sort by in a mappingClear intent, no code
Logic that formulas cannot express (loops with state, special algorithms)JavaScript codeFull language, sandboxed, with a time limit
Libraries of a language (data science, a vendor SDK)Python script, PowerShell scriptRuns on the server; needs scripts allowed by an administrator
Parse or render a formatParse JSON, Render JSON, Parse XML, Render XML, Parse CSV, Render CSV, HTML templateChecked against the schema, errors on bad input
  • Should: prefer mappings and formulas to code. A reviewer can read a mapping; code needs reading line by line, and it hides fields from the data trees.
  • Should: one mapping step instead of a chain of small transform steps; every step costs a save and a round trip.
  • Must: code steps have no side effects beyond their output (no files, no network) unless that is their documented purpose.

Writing formulas

Formulas start with = in a plain field and are implied in mapping targets. References are in braces: {input.orderId}, {nodes.Find the customer.rows}, {vars.1.batchNo}, {gv.INVOICE_FOLDER}. The full list is the Function reference; Sample: Functions (New Sutra, Samples) runs every one of them on an order.

  • Should: reference earlier steps by name ({nodes.Find the customer}) rather than {input} when the value comes from further back: it survives inserting a step in between.
  • Should: keep a formula to one line a reader can follow; split a long one over two mapping fields or use Transform (JSONata).
  • Must: handle missing values on purpose. A field that may be absent gets a default (if(empty({input.note}), '', {input.note})) rather than leaking null into a target system.

Function groups: patterns and pitfalls

  • For-Each over a list with Where (skip lines), Sort by and Group by (one target line per group with {group.key}, {group.count}, {group.items}); position() numbers lines. Sample: For-Each mapping shows each.
  • Should: map against a schema on both sides, so the mapper checks every target field and the designer warns about a missing source.
  • Should: look up codes (country names, tax rates, product groups) in a memory table or a small reference table, not in long nested if formulas.

6. Reusable logic: called Sutras, variables and counters

A called Sutra is SutraFlow's function: it takes an input, does one job and hands back a result with Return. Call Sutra calls it, with Wait on to continue with the result.

Designing a called Sutra like a function

  • Must: an input schema and a result schema, with Validate input and Validate result on for shared Sutras: the contract is checked on every call, and the data trees of callers show its fields.
  • Must: every path ends in Return (or fails). A path that just ends leaves a waiting caller without a result.
  • Should: a pure function where possible: the same input gives the same result, no changes outside. Sutras that do change things say so in their name (Reserve stock) and are safe to repeat.
  • Should: callers use the deployed version (the default while not testing is deployed (draft while testing)), so a half-finished draft never runs in production.
  • Should: keep it small and generic: Calculate tax takes an amount and a country, not a whole order.
  • May: call without waiting to start independent work (a notification, an audit copy). Its failure does not reach the caller, so it needs its own error handling.

One run per item

For work on many items with several steps each, call a sub-Sutra per item from a For each: each item gets its own run, retries and history, and items run in parallel on free workers. A failed item can be found and run again on its own.

  • Must not: use a local variable to pass data between runs; it lives for one run. Use a counter, memory table or database.

7. Data contracts and schemas

A contract is the agreed shape of a document: what a caller sends, what a Sutra returns, what goes on a queue. In SutraFlow it is a shared schema (JSON Schema or XSD) or a WSDL in the project (Schemas and WSDLs).

  • Must: every public entry point (REST body, SOAP operation, queue message, channel, called Sutra) has a schema.
  • Must: validate untrusted input against it at the door: REST Validate body: reject invalid (a 400 with the problems), SOAP against its WSDL, queue messages with Validate fields before any change. Strict validation on Manual start, Call Sutra and Return checks the rest.
  • Should: a canonical document per business object inside a domain (one Order shape), with mappings at the edges to and from each partner's shape. Partners change; the inside stays stable.
  • Should: describe fields in the schema (description), with formats (date-time, email), patterns and enumerations; the gateway's OpenAPI and the generated documentation show them.
  • Must: run Check schema change impact before saving a change to a shared schema: it lists the Sutras and mappings affected.

Changing a contract

ChangeBreaks callers?How
Add an optional fieldNoAdd it; callers that do not know it ignore it.
Add a required field to a requestYesMake it optional with a default first; require it in the next version.
Rename or remove a field, change a typeYesNew version of the schema and of the entry point (/v2/orders, Order v2); run both until callers have moved.
Add a value to an enumeration in a responseMaybeTell callers first; strict clients may refuse unknown values.

The same Sutra runs on development, test and production. What differs is configuration (Variables and the deployment config).

APIs and web services

9. REST API design

A REST service is a REST service trigger with a path and a method, answered by Send HTTP response. The gateway serves it, checks its policy and lists it in OpenAPI (The API gateway).

Resources and paths

  • Must: paths name resources, not actions: GET /v1/orders/:id, not /getOrder. Plural nouns, lower case, hyphens.
  • Should: one Sutra per method and path, or a small group of closely related ones; a Sutra that answers ANY and branches on the method is harder to secure and document.
  • Should: a version at the front of public paths (/v1/); internal services between your own Sutras may leave it out.
  • Actions that are not create, read, update or delete become sub-resources: POST /v1/orders/:id/cancellation.

Methods

Status codes and errors

CodeWhen
400The request is wrong: failed validation, a missing field. Say which fields.
401 / 403Not signed in / not allowed. The gateway's policy answers these before the Sutra runs; your Sutra answers 403 for business authorisation (a customer asking for another customer's order).

Must: every error answer has the same body shape across the project, for example:

{ "error": { "code": "ORDER_NOT_FOUND", "message": "Order A-1001 was not found", "details": [], "runId": "..." } }
  • Must not: put stack traces, SQL, host names or secrets in an answer. Log them; answer with a code and the run id so support can find the run.
  • Should: an Error handler in each API Sutra that replies 500 with the standard body, so an unexpected failure still answers.

Safe to repeat, asynchronous work and large lists

  • Should: POST that creates is made safe to repeat with a business key the caller sends (an order number, or an Idempotency-Key header kept with the result): a second call with the same key returns the first result instead of creating twice. A unique key in the database enforces it.
  • Must: work that takes longer than a few seconds answers 202 with a job id at once and continues after the reply (Send HTTP response early, or Call Sutra without waiting); a GET /v1/jobs/:id service reports progress. Raising Reply wait is the last resort.
  • Should: lists are paged (?limit=50&after=A-1001) with a maximum page size, and filtered by query parameters, never returning a whole table.
  • Should: set Max body size to what the service needs (1024 KB by default); bigger documents are uploaded as files.

Documentation

The gateway builds OpenAPI from deployed REST services, their policies and body schemas (Admin Console, Gateway, APIs; published on the gateway when chosen). Should: a body schema with descriptions and a realistic test request on every service: the OpenAPI document, the designer's test run and sutra test all use them. Sample: JSON microservices shows three services that call each other.

10. SOAP web services

SOAP services are contract-first: the WSDL comes first, the Sutras follow it. SOAP service serves operations of a WSDL on the gateway (and generates a WSDL when you start without one); SOAP reply answers; Invoke SOAP service calls other SOAP services.

  • Must: import or write the WSDL (and its XSDs) into the project before building; agree it with the consumers.
  • Should: one Sutra per operation for busy services, or one Sutra with a Switch on the operation for a small service; the WSDL stays one document either way.
  • Must: business errors answered as SOAP faults with a fault code and a readable string (and a detail element when the WSDL defines one), not as a normal response with an error flag.
  • Should: build replies with Map XML Data against the WSDL's types, so the reply is checked before it leaves.
  • Must: a security policy: WS-Security UsernameToken with a time window and replay protection, X.509 signatures and encryption, SAML assertions, or mutual TLS (Exposing APIs: security and TLS).
  • Should: give consumers a mock first: a SOAP service with canned replies from the WSDL, so they build while you do. Sample: Mock SOAP service and its caller shows one.
  • Calling a SOAP service: Invoke SOAP service with the partner's WSDL, a connection with its security profile, its fault output connected, and a timeout that fits the partner.

11. API security and the gateway

Every request to a deployed Sutra passes, in order: the firewall, the service's security policy (HTTPS, IP rules, authentication, rate limit, CORS), the scopes the service requires, and for gateway apps their plan. A refused request never starts the Sutra.

  • Must: every entry point on the gateway (REST, SOAP, WebSocket, MCP, agent channels) has a security policy. The designer and Deploy warn about one without.
  • Must: Require HTTPS stays on for anything reached over a network you do not control.
  • Should: choose authentication by caller: API keys for a few systems of your own, gateway apps (an app per caller with scopes, a plan and keys or OAuth client-credentials tokens) for partners, JWT from the company's identity provider for its users, mutual TLS for closed B2B links. The user guide's Designing Sutras has the full table.
  • Should: scopes per service and operation (orders:read, orders:refund); a caller gets only the scopes it needs.
  • Must: authorisation inside the Sutra for data that belongs to someone: the caller's identity is {trigger.auth.subject} (and {trigger.auth.claims} for JWT); a customer reads only rows where the customer id is theirs.
  • Should: a rate limit on every public policy, and plans per gateway app, so one caller cannot starve the others.
  • Should: CORS origins only for services browsers call, listing the real sites, never * with credentials.

Behind a reverse proxy or load balancer

When Apache, nginx, IIS or a cloud load balancer is in front of SutraFlow, list it under Admin Console, Gateway, Firewall, Trusted proxies (2.1.4). From a trusted proxy, SutraFlow reads the caller's real address (X-Forwarded-For) and the HTTPS the proxy ended (X-Forwarded-Proto); from anyone else it ignores both. Without it, every caller has the proxy's address, so IP rules and per-address rate limits treat all callers as one, and Require HTTPS refuses calls forwarded over plain HTTP. Must: list only proxies that replace those headers, never a range callers reach directly. The Administration Guide has the proxy settings (Planning a server).

13. WebSockets, AI tools and agent endpoints

WebSocket services

  • WebSocket service starts a run per message (in order per connection unless the service says otherwise); WebSocket send answers one connection or broadcasts to every connection of a service, across engines.
  • Must: a policy (browsers send a token or key in the query) and CORS origins for browser clients; size, depth and schema limits on messages.
  • Should: clients reconnect with a pause and treat broadcasts as notices, not a ledger: a client that is reconnecting (after a network drop or an engine stop) misses what was sent meanwhile. Keep the state in a system the client can read again (a REST service) and use the broadcast to say "read again". Since 2.1.4 a just-connected client gets the next broadcast, and an engine that died no longer collects broadcasts to send to the wrong clients later.

AI tools (MCP) and agents

  • An AI tool is a Sutra with AI tool and Reply to AI: design it like a REST service with a schema, a policy and a clear description, because the model reads the description to decide when to call it.
  • Must: tools that change data check the caller and the input inside the Sutra; the model is not an authorisation layer.
  • Should: AI guard before agents on public entry points; limits on steps, tokens and time; Ask a person for anything with risk. The user guide's AI agents and knowledge bases has the details.

Orchestration or choreography

Orchestration: one parent Sutra calls the others in order and knows the whole process; easy to follow and to change, one place to see where a process stopped. Choreography: each Sutra reacts to events and publishes its own; parts are independent, but the process exists only as the sum of the reactions. Should: orchestrate a business process with a clear owner and order (an order from payment to shipping); use events to tell other domains what happened (order.shipped), so they do not depend on your process.

16. Files and batch processing

  • Must: a file trigger waits until the file is complete (stable for some seconds), and a file is moved to a processed/ or error/ folder after the run, so it is not read twice and failures can be found (Files).
  • Should: one run per file: a trigger per file, or a list without reading and a sub-Sutra per file.
  • Must: big CSV and line files are streamed (Stream in batches), never read whole. Batches go out on the batch output while reading goes on; reading pauses while too much waits (back pressure: the number of waiting batches, and since 2.1.4 also 8 MB of input in flight), so memory stays the same for 10 MB and 10 GB.
  • Should: Step data in history set to none for streaming Sutras; every batch is otherwise kept until the run ends.
  • Should: batch sizes of 1,000 to 5,000 rows; each batch is a step and counts towards Steps per run.
  • Should: database batches paged by key (where id > :last order by id limit 1000), one page per run or per sub-Sutra call, with the last key saved, so a stopped batch continues where it was.
  • Should: SFTP and FTP with the host fingerprint checked and a key rather than a password; archive names with a date.

Learning big documents into a knowledge base: stream them in parts of a few thousand lines into Add to knowledge with a source name per part, into a pgvector knowledge base for large volumes. Measured in 2.1.4: a 48 MB document in 54 parts, about 140 MB of live heap at 32 workers, and back to the starting memory after the run.

18. Error handling, retries and compensation

Decide for every kind of failure where it is handled and what the caller or the operator sees.

KindExampleRetry?Handle by
ValidationA required field is missingNoReply 400 (or a SOAP fault, or dead-letter the message) at the door
BusinessNot enough stock; credit limit reachedNoA normal branch (an If), a 409 or 422 reply, a message to a person
Transient technicalA timeout, 503, a dropped connectionYes, with backoffStep retries; after the last one, the error output
Permanent technical401 from a partner, a missing table, bad configurationNoError output or Error handler: alert, reply 500/502, stop

Where to handle

  • Error output of a step: for failures you can do something specific about (a fallback, a cached value, a clear reply).
  • Error handler (Error handler): runs when a step fails and its own error output is not connected; other branches stop. Should: one per Sutra for the common response: log with the input, alert, reply 500 to an API caller, dead-letter a message.
  • Throw error: fail on purpose with a message when a business check fails deep in a branch and the Error handler should take over.
  • End with an error status: end the run as failed after handling, so it shows as failed in Runs and in alerts.

Retries and timeouts

  • Should: 3 retries with a 1 s first wait (doubling) on calls to other systems that are safe to repeat; set them once in Sutra tuning (Retries, First retry after) and override on single steps.
  • Must not: retry what is not safe to repeat (a payment without an idempotency key) or what cannot succeed (validation, 401, 404).
  • Should: a run time limit on Sutras that wait (approvals, long jobs), so forgotten runs end.

Compensation

Several systems rarely share a transaction. When step 3 of 4 fails after steps 1 and 2 changed other systems, undo them: each changing step has an undo (release the stock reservation, refund the payment), and the error path runs the undo steps of what succeeded, in reverse order. Must: undo steps are safe to repeat and are themselves retried; a failed undo alerts a person.

What the outside sees

  • Must: callers get a standard error body with a code and the run id; operators get the full detail in the run and the log.
  • Should: alert rules (Admin Console) on failed runs, slow runs and waiting approvals, rather than people reading logs.

19. Logging, audit and traceability

  • Should: one or two Log lines per run at info for business milestones, with the business keys: Order A-1001 accepted: 3 lines, 2,450 INR. The run id is added for you.
  • Should: warn for unexpected but handled; error for what a person must look at; debug only while finding a problem (the user guide's level table).
  • Must not: log secrets, passwords, tokens, card numbers or whole personal records. Secret values are masked; other personal data is the designer's care.
  • Should: Step data in history (Sutra tuning) all while building, errors only for busy production Sutras, none for Sutras with sensitive data or streaming.
  • Should: a correlation id through every hop: the business key in logs and messages, the run id in error answers and as the message correlation id, and traceparent on HTTP calls (passed on for you) so traces join across systems.
  • Where logs go: the run's log and each step's Output tab (2.1.3), the project log file (Project, Logging; JSON for collectors), metrics at /metrics and traces to an OpenTelemetry collector (Trace sampling).
  • Audit: who changed, deployed or approved what is kept by SutraFlow in the audit log; your Sutra records business decisions (who approved a refund) in your own system.

20. Microservice design with Sutras

A microservice is a small service that owns one business capability and its data, and can be changed and released on its own. In SutraFlow a microservice is a set of Sutras behind gateway paths, with their own connections and schemas, usually one project or one folder of a domain project.

Boundaries

  • Should: draw boundaries around business capabilities (customers, stock, orders, invoices), not around technical layers (a "database service", a "mapping service").
  • Must: a service owns its data. Other services ask it through its API or react to its events; they do not read its tables.
  • Should: a project per service when teams release separately; folders of one project when one team owns several small services that are released together.
  • Should: size by change: things that change together belong together. A service that cannot change without three others changing is too small (or the boundary is wrong).

Talking to each other

StyleUse whenWith
Synchronous request (REST, SOAP)The caller needs the answer to continue (price, stock check)Send HTTP request to the other service's gateway path, with timeout, retries and a circuit breaker
Asynchronous eventOthers should know something happened; nobody waitsPublish message of order.accepted; subscribers in their own services
Asynchronous commandAsk another service to do work, answer laterA message to its queue, a reply message or callback
  • Should: prefer events between services; a chain of synchronous calls (A calls B calls C) fails when any of them fails and is as slow as their sum.
  • Must: a synchronous call between services has a timeout shorter than the caller's own reply time, and a fallback or a clear error when the other service is down.
  • Should: services call each other through the gateway with a policy (an internal API key or a gateway app), like any other caller; never by reaching into another project.
  • Should: each service publishes its API (OpenAPI from the gateway) and its event schemas; consumers code against those, not against its Sutras.

25. Blueprint: integration through a message broker

A broker (Kafka, RabbitMQ or ActiveMQ) between systems lets each work at its own pace and survive the others being down. Sample: Queue in and out and Sample: XML queue in and out are the starting point.

Design

  1. Events and commands: an event says what happened (order.accepted, on a topic, many subscribers); a command asks one system to do something (invoice.create, on a queue, one consumer).
  2. One canonical message per business event, with a schema, a message id, a correlation id and a timestamp; partner formats are mapped at the edges.
  3. Receiving: Queue / topic trigger with Acknowledge: explicit when the work ends by publishing, client otherwise; Deduplicate on with a duplicate key; On failure: reject (dead-letter) after a few redeliveries.
  4. Consume, transform, publish: map, publish and wait for the broker to accept, then Confirm, as the sample does. A message is never confirmed before its result is safely out.
  5. Dead letters: a Sutra (or an alert) on each dead-letter queue: log the message with its keys, tell a person, and offer to resubmit once fixed.
  6. Order: where order per customer matters, the Kafka key is the customer id and concurrency stays per partition.

Packaging

  • Broker connections per environment: the host, port, TLS files and user come from properties, the password from the vault; the samples' connections (Sample Kafka (TLS + SASL), Sample RabbitMQ (mutual TLS)) show every setting as a property already.
  • Queue and topic names as properties ({{gv.ORDERS_QUEUE}}), so test and production can share a broker without sharing queues.

Broker REST or native

Sample: Broker REST APIs publishes and fetches through Kafka REST, RabbitMQ HTTP and ActiveMQ Jolokia: use it only where a network allows nothing but HTTPS. Native Queue / topic triggers keep the connection open, acknowledge properly and scale; prefer them.

AI workers on a queue

Rules

  • Must: learn only what the people who will ask may see. Published products for a public chat; for staff, the internal fields too, in another knowledge base or with a detail (audience = staff) and a filter in the search.
  • Should: one source per item with a stable key; never one source for the whole table (a change would make every vector again).
  • Should: build the text the way a person would ask about it: "Assam tea, 250 g. Category: Tea. Price: 180 INR. Strong, malty black tea…". Codes and ids alone match nothing.
  • Should: details for what an answer needs to show or filter (category, price, link, language, date); the search returns them with each passage.
  • Should: the table, the query and the schedule from project properties, so the same feed reads test and production databases.
  • Should: big tables paged by key, or only the rows changed since the last feed (where updated_at > :last, the mark kept in a counter or a table), with a full run with keep only now and then.

A Joomla site

Give SutraFlow a database user that can only read those tables.

Answering from it

  • Search knowledge: the closest passages with their details, no AI model needed: a search API, a "related products" list.
  • Ask knowledge: a written answer from the passages, with sources (an AI provider).
  • An AI agent with the knowledge base: a chat that can also use tools (stock, orders), as in Blueprint: chat agents.

One knowledge base for many projects

A plain feed (a folder, SharePoint, a table) can be a managed source with no Sutra at all; when it needs shaping, export it as a Sutra and change that. 29. Blueprint: dashboards

  • One dashboard, one question: "How are sales going?", "Is the warehouse keeping up?". Four to eight charts; a number for the headline, a line for the trend, a bar for the ranking, a table for the details.
  • Push the work down: aggregate in SQL (group by month), never fetch raw rows to count them in a Sutra.
  • Parallel queries: each chart's query on its own branch from Dashboard page, joined by a Merge before Dashboard reply.
  • Refresh to match the data: a minute for operations, an hour for sales by month. The shared cache means viewers cost nothing between refreshes; a dashboard that shows each caller their own data caches per caller.
  • Must: a security policy on every dashboard that shows anything not public. The page holds no data; the data request goes through the policy.
  • Should: read-only database accounts for dashboard queries, and connection limits on busy databases.
  • Filters: three to five slicers on the fields people ask by (region, product group, period). On a database, filter in SQL with bound parameters; on JSON, let the Chart steps filter. Give list filters their choices from a small DISTINCT query.
  • KPI cards first: two to four figures at the top, each with its comparison (the period before or a target), then the trend, then the breakdowns.
  • AI suggestions: let a model choose chart types and titles, never the data; the Chart step and Charts from AI check every suggestion against the allow-list. Send it only field names and kinds when the data is confidential.
  • Embedding: /dash/<name>/embed.js on an intranet or customer portal, with the portal's login passed as for the chat button (Blueprint: chat agents).

Design checklist for an AI application

  • Which agent: a public agent that owns the conversation, or skills for an outside assistant (Blueprint: chat agents).
  • Who is asking: from the login token, never the message; data filtered by subject.
  • What the model may do: narrow steps, tools as Sutras, limits on steps, tokens and time; people before risk.
  • What it knows: knowledge fed on a schedule with stable sources and keep only; nothing the askers may not see.
  • How long it remembers: the conversation lifetime per agent, and expired conversations cleared on a schedule.
  • How you know it works: runs traced, dashboards for operations, test questions for each role kept beside the project.

31. Error handling through logs, and traceability

When a customer calls about order A-2001, anyone on support should get from the order number to the project, the Sutras it went through, every run and every step, in a minute. That needs a little design in every Sutra and the right settings.

1. Design every Sutra for it

  • A correlation id made once, at the door, from the business key (ord-A-2001) or taken from the caller's header, and passed on in every called Sutra's input, every event and every message (as the message's correlation id).
  • Log lines with the keys: business key, correlation id, and the run id: Order A-2001 received for 1800 INR [correlation ord-A-2001, run {{run.id}}]. The run id is also added to every line by the project log; putting it in the message makes it searchable everywhere the line is copied to.
  • Events carry the sending run (sourceRun: {run.id}), so a run started by a channel or a queue can be traced back.
  • Errors logged with the same keys on every error output and in the Error handler: Credit check failed for order A-2001: … [correlation ord-A-2001, run …].
  • Error answers carry the run id, so a caller's support ticket points straight at the run.

3. Trace an order, step by step

With Sample: Traceability and notifications added: deploy Sample: Trace notification hub, then test Sample: Trace order intake.

  1. Project: Admin Console, Traceability lists every project with its runs by outcome; open the project for its Sutras with success rate, last run and last failure.
  2. Find the run: Find a run with A-2001 (a value in the data a run started with), a run id or its first characters, or who started it. The intake run and the hub run both started with the order number.
  3. The run: its ids (run, Sutra, project, each with Copy), who started it, what it started with, every step with status, try, time, engine, error and its input and output, its reply and its log.
  4. Across Sutras: the intake run shows the credit check it called (Call Sutra) and the credit check shows the run that called it, each a click away. The hub run, started by the channel, names the intake run in its log line (from run …), and the correlation id finds both in the project log.
  5. The log: Configuration, Project log, filter by ord-A-2001: every line of every Sutra for that order, in time order.
  6. Keep the evidence: Download saves the whole run as JSON for a ticket.

4. From an error to its fix

  • Alert rules (failed runs, slow runs, gateway errors, listeners in error) notify by email, webhook or a Sutra, with the Sutra and the count; the Overview lists the latest failed runs.
  • Open the failed run in Traceability: the failed step, its input, the error, the retries.
  • Fix the cause (data, a partner, a connection, or a new version of the Sutra), then Resubmit the run from the Overview or the Sutra's runs.
  • Gateway, Traffic and the request log show the same calls from the caller's side: path, app, status, time and the run they started.
  • Across systems: traceparent is passed on HTTP calls and traces go to an OpenTelemetry collector (Trace sampling), so a call from a mobile app through SutraFlow to the ERP is one trace.
The rule of three keys

Every log line, event and error answer carries the business key, the correlation id and the run id. With those three, any order can be followed from the project to every Sutra and run.

40. Testing Sutras

  • Must: every trigger has realistic test data (test request, test message, payload): the designer's Test, sutra test in a pipeline and the documentation use it (Testing and debugging).
  • Should: test the unhappy paths too: invalid input, a missing record, a partner that answers 500 or is slow. A Sutra whose error paths never ran is not tested.
  • Should: mock partners that are not ready or not available in test: a REST or SOAP service of your own with canned replies, pointed to by a property.
  • Should: called Sutras tested on their own with their input schema, like unit tests of a function.
  • Should: breakpoints and step-by-step debugging for logic, the Output tab (with each step's log lines) for what a step really received and produced.
  • Must: sutra test in the release pipeline, so a broken Sutra stops the release (CI/CD pipelines).

41. Versions, releases and environments

  • Must: the project in Git: a branch per change, a review before merging, a tag per release (Git).
  • Must: one release package built once, from the tag, promoted unchanged to test and production with each environment's deployment config; production refuses deploys from the designer (Releases).
  • Should: version numbers that say what changed: patch for fixes, minor for added fields and services, major for changes that break callers.
  • Must: a change that breaks callers gets a new API version beside the old one; the old one is retired when its callers have moved.
  • Must: database changes travel with the release, as scripts that run twice safely.
  • Should: know the way back before deploying: roll back to the previous release; runs in progress finish on the version they started with.
  • Samples are learning material and starting points. A Sutra built from one is designed, tested and released like any other; a sample never goes to production as it is.
