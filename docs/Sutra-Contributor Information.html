1. Who this is for

This document is for contributors: people who change SutraFlow itself, its server, studio, Admin Console, Approval Center, tests, documentation and release builds. Everything about using SutraFlow (designing Sutras, mapping, activities, deploying, administering, approving) is in the user guide; how the parts fit together and what every file does is on the architecture page. Both are generated from the source and served by every server at /guide and /architecture.

  • Never edit a generated file by hand: docs/sutraflow-user-guide.html, this document, docs/sutraflow-architecture.html, docs/code-navigation.md and the file overviews are written by the tools below.
  • Release notes (RELEASE-NOTES.md) record every fix in plain words: what a person saw, the cause, and what happens now.
  • Work not done belongs in docs/backlog.md, prioritised with MoSCoW; an item that ships is removed in the same change.

2. Build and run from the source

Requirements: Node.js 22.13 or later (24 recommended) and Git. On Windows the shell commands work in PowerShell or Git Bash.

  1. Open a terminal in the SutraFlow folder.
  2. Install and build: bin/sutraflow setup (Windows: bin\sutraflow.cmd setup). It runs npm install and npm run build, and makes sutraflow.env, where the ports, the data folder and the database are set.
  3. Start: bin/sutraflow start, then bin/sutraflow open (http://127.0.0.1:4800). The first time, create the administrator account.

For development with automatic reload, run npm run dev and open http://localhost:5173: the server restarts on a change (tsx watch) and the web pages reload (Vite).

CommandWhat it does
npm run buildThe web pages (Vite: designer, Admin Console, Approval Center) and the server (TypeScript to dist/); checks the vendored packages first.
npm run typecheckServer, web pages and tests, without writing files.
npm testBuilds, then runs every test suite (see Tests).
npm run guide, npm run architecture, npm run samplesThe user guide and this document, the architecture page, and the sample project archives.
npm audit --audit-level=highKnown vulnerabilities in the dependencies; the release gate expects none.

4. Every file carries its signature and overview

Every first-party file starts with two comment blocks:

  1. The header: SutraFlow, the copyright and developer line, the file version (the version the file first appeared in) and the licence (AGPL-3.0-only, with the commercial licence note). node tools/add-headers.mjs adds it to files that have none, with the current version from package.json; it never changes an existing header.
  2. The file overview: the file's purpose (from its description on the architecture page), the modules it imports and the functions it declares. node tools/file-overviews.mjs writes it; --check fails when any overview is out of date, and a test runs that check.

So a new file needs: a description in tools/build-architecture.ts (the architecture page also lists files without one), then node tools/add-headers.mjs and node tools/file-overviews.mjs. Formats without comments (JSON, private state) are listed in docs/code-navigation.md instead. Vendor code, compiled output and binary files are left alone.

5. Tests

npm test builds and runs every suite with the Node.js test runner, two files at a time. Each suite gets its own data folder, master key and ports (test/helpers.ts). The PostgreSQL-compatible pass (test/postgres.test.ts) runs the in-process suites again on PGlite.

Real services are used when you point the tests at them; otherwise those tests are skipped and say what they need:

VariableRuns
SUTRA_TEST_PG_URLReal PostgreSQL: pooled engine, outage and reconnect, two engines, migration, connection limits with two engines. An administrator address; each test makes a database of its own and drops it.
SUTRA_TEST_PG_BINThe password-and-SSL migration (a temporary PostgreSQL cluster from these binaries).
SUTRA_TEST_MYSQL_URLReal MySQL: bound parameters, transactions, install scripts, procedures.
SUTRA_MONGO_TEST=1, SUTRA_MONGO_TEST_ENV_FILELive MongoDB Atlas M0 (seeds and removes its own records); the file holds the URI, user and password.
SUTRA_KAFKA_TEST, SUTRA_RABBITMQ_TEST, SUTRA_ACTIVEMQ_TEST, SUTRA_BROKER_REST_TESTReal brokers with TLS and their REST checks.
SUTRA_TEST_TIME_FACTORStretches the time budgets of timing-sensitive suites. The connection-limit suite measures the database itself: 15 times for a database over the internet, where an operation takes 650 to 750 ms.
  • A test that creates a second engine in one process must give it a heartbeat (insert it into engines), or the leader recovers its running steps as orphans and runs them again.
  • The README test badge must equal the number of declared tests; a regression test checks it.
  • npm run test:samples checks every bundled schema and starter payload and runs the connection-free validation and mapping fixtures. Broker and other external samples need their real-service tests.
  • Security regressions live in test/security210.test.ts and next to the feature they protect: add a test that reproduces an attack before fixing it.

6. Security rules for contributors

  • Paths in data: read and write data paths only through getPath/setPath (server/src/values.ts); __proto__, prototype and constructor are never data field names. Build objects from data with Object.fromEntries.
  • Permissions: every Admin API route has a rule in guard.ts; check a caller with can() or isAllCaller(), never by reading a flag that could be inherited.
  • Projects: work runs as its project (inProject in resources.ts); a lookup inside it refuses another project's connection. New entry points that run work must set it.
  • Secrets: a secret value never appears in a message, a log line, an API answer or the Admin Console; describe the problem instead of repeating a resolved value.
  • SQL: values are bound parameters; run data written in SQL text is turned into parameters (inlineRunData).
  • HTML: escape text and attributes; a value written into a script is serialised script-safe (escape <, >, &).
  • Outside files and archives: read repository files through repoFile() (no .., no symlinks out); unzip with limits on the real output.
  • Owners: a job or a conversation belongs to its caller's realm, method, subject and app; compare all of them.

7. Vendored packages

vendor/ holds packages maintained here because the published version had a problem (a vulnerable dependency, an unneeded part). vendor/vendor-lock.json pins each one to its npm version and integrity, a hash of the local tree, the reasons for each change, who uses it, its tests and whether it ships. npm run vendor:check (part of every build) fails on any drift; vendor:check:online (CI) also fails when npm publishes a newer upstream version, which then needs a review, the changes applied again and the full regression suite.

8. Release builds

  1. Bump the version in package.json (and package-lock.json), the README badges, the Docker and guide examples.
  2. Write the release notes, with the release gate and the Fixes table.
  3. npm run guide, npm run architecture, npm run samples, node tools/add-headers.mjs, node tools/file-overviews.mjs.
  4. The full test suite with the real services you have.
  5. npm run build, then node tools/build-release.mjs (add --offline for an archive with the runtime packages inside, for the system it runs on). It writes release/sutraflow-<version>-windows.zip and -linux.tar.gz with .sha256 files.

A release holds the built server and web pages, the launcher, the user guide and architecture page, deployment templates, runtime tools, samples and the licences. It never holds the source, tests, benchmarks, this document, development tools or node_modules (except in the offline archive). Test a release with a clean install and an upgrade from the previous one, on SQLite and PostgreSQL.

9. Load, soak and big-file tests

These tools live in the source repository only; they are not part of the release packages. The measured results are in the user guide (Sizing and performance) and in docs/benchmarks.

Soak test: hours of mixed load, unattended

tools/soak.mjs runs a studio and engines on a PostgreSQL database of their own for hours and writes its own report (report.md and report.html).

node tools/soak.mjs --pg postgres://postgres@db:5432/postgres --hours 8
node tools/soak.mjs --pg ... --hours 24 --share //fileserver/soak     # the folder trigger watches a real share
node tools/soak.mjs --report-only docs/benchmarks/soak-1.8.0               # the report again, from the samples

It exercises every starter that runs on one machine (REST plain, in memory and HMAC-signed; SOAP with UsernameToken and with X.509 signing and encryption; WebSocket service and client; timers; called Sutras with approvals; the error handler; channels; FTP and SFTP), big files streamed (CSV of 10 to 60 MB through a folder, SFTP and FTP; documents into pgvector; Google Drive when an account is set), and faults on purpose (an engine killed a third of the way in, the database cut for 20 seconds two thirds of the way in). It checks that no engine stopped by itself, no run was left open, no step ran twice, failed requests stay under 0.5%, timers were on time, every message and file row was handled, memory stayed steady and engines stayed responsive.

For Google Drive, set SOAK_GOOGLE_CLIENT_ID, SOAK_GOOGLE_CLIENT_SECRET (a Desktop app OAuth client of your Google Cloud project) and SOAK_DRIVE_FOLDER (the folder id), then run node tools/soak.mjs --google-sign-in once.

Load test and big files

node tools/loadtest.mjs --pg postgres://user:pass@db:5432/postgres --engines 1,2,4 --payload 0.1,64 --out results.json
node tools/loadtest.mjs --sqlite --cpus 1 --mem 512 --workers 4 --execution durable,memory
node tools/loadtest.mjs --pg ... --engines 2 --kill        # kill one engine under load, check nothing is lost
node tools/loadtest.mjs --pg ... --soak 60                 # an hour of timers, waits, failures and a redeploy
node tools/bigfiletest.mjs --mb 1000 --mem 384             # stream a 1 GB file with a 384 MB heap

The PostgreSQL address is an administrator connection: the test makes a database of its own for each scenario and drops it afterwards. --cpus and --mem hold each engine to that many cores and that heap.
