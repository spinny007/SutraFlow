What SutraFlow is

SutraFlow is an integration designer and engine. People draw Sutras (integration processes) in a browser studio, and the engine runs them: REST and SOAP services, file and database jobs, queues, email, cloud apps, scripts, AI steps and skills for AI assistants. One Node.js program holds the studio, the engine and the gateway; the same program runs headless in production, alone or as a cluster on PostgreSQL.

The running server

Everything runs in one Node.js 24 process written in TypeScript. Its parts:

  • Admin API (Fastify, port 4800, 127.0.0.1 by default) serves the studio, the user guide, this page, and every editing and operations route. People sign in with a session cookie; automation uses Authorization: Bearer <SUTRA_ADMIN_TOKEN>.
  • Gateway (ports 8080 and 8443) serves only what is deployed: REST paths, SOAP services with their WSDL, and MCP endpoints. It is separate from the admin port so the studio never has to face the internet.
  • Engine runs steps in worker slots (SUTRA_WORKERS, set by the machine size by default). Slots take tasks from the database. Sutras tuned to run in memory go to a second engine in the same process whose runs live in a private in-memory database and are written to the database in one transaction when they end.
  • Timers and listeners start runs from schedules, folders, mailboxes, queues and Drive. In a cluster they run on the leader only, so nothing starts twice.
  • Cluster beat writes this engine's heartbeat, holds or watches the leader lease, recovers dead engines' steps, and reloads routes after deploys elsewhere.
  • Memory tables keep small reference data (rates, codes, routing, reusable values) in each engine: an LRU JavaScript Map per table inside the Node.js process. Each table, project and engine has row and byte quotas. Refresh creates a replacement off to the side and swaps it only after its query, keys and quotas pass, preserving the last good copy on failure. Failsafe tables schedule on the leader and use mem_rows/mem_meta versioning; memory-only tables schedule on every engine.
  • Storage is SQLite in the data folder, or PostgreSQL for several machines. Sutras, runs, tasks, the vault, settings and cluster state all live there.

The internal queue bus

The engine bus is deliberately a durable database queue with a fast wake-up signal, not a second message broker. The tasks table is the source of truth. Starting or routing a run inserts a pending task in the same transaction as the run checkpoint. PostgreSQL transactions use the main-thread pg.Pool; each transaction keeps one checked-out connection and takes the appropriate advisory per-run lock. The claim counter is increased every time a task is claimed and is included in every completion fence.

  1. A transaction commits a new pending task. A database trigger calls pg_notify('sutraflow_queue', '') only after that transaction commits.
  2. Every worker engine has one dedicated LISTEN sutraflow_queue connection. A notification coalesces into scheduler.wake(); it does not carry the task or assign it to an engine.
  3. Free slots race through the atomic claim statement. PostgreSQL SKIP LOCKED lets engines take different rows instead of waiting behind one claim.
  4. Periodic polling always continues. It covers a lost notification, listener reconnect, work that becomes due after a retry delay, and SQLite, which has no LISTEN/NOTIFY.

This design keeps one recovery model: after a restart or network interruption the engine reads durable rows and needs no replay log held by another service. Notifications reduce idle latency and database polling traffic without being trusted for delivery. Set SUTRA_PG_NOTIFY=0 to test or operate with polling alone.

How a run works

  1. Start. A trigger (or a test run, the Run API, a channel, Call Sutra, an MCP call) calls startRun. It inserts the run row, which keeps a copy of the Sutra document it started with, and one pending task for the trigger step. Redeploying never changes a run in flight.
  2. Queue. A deployed Sutra tuned with Runs at once starts extra runs as queued; they move to running, oldest first, when one of its runs ends (and the leader checks on each beat).
  3. Claim. A free worker slot claims the next due task, highest Sutra priority first, with one atomic statement: update tasks set status='running', owner=? where id = (select ... where status='pending' and not_before <= now order by priority desc, id limit 1) and status='pending' returning *. Two engines can never claim the same task.
  4. Run the activity. The engine resolves the step's settings (templates, formulas, Project and Engine properties, secrets) and its Input mapping, then calls the activity's execute with a context (logging, secrets, abort signal, time limit). Loop settings run it once per item of a list, or again while a condition holds, and collect the results.
  5. Checkpoint. In one transaction the engine stores the step's output, marks the task done, and inserts tasks for the next steps. A crash before the commit leaves the durable task unfinished; the activity may therefore run again after recovery. A crash after the commit finds the completed transition and its next tasks. The claim fence makes the durable transition apply once even if an old worker returns late. Nothing required for continuation is kept only in memory between steps.
  6. Route. The step's result names a port (out, error, ok, problems, approved, rejected...). Each connection from that port carries a live token or a skip token according to its condition. A merge waits for a token on every incoming connection.
  7. Finish. When no tasks remain the run is done; a failure with no error path fails the run; End and stop options (this branch, Sutra success, Sutra error) finish early. The run's status, duration and steps go to metrics, traces and logs.

Task states

Connections, conditions and merges

A connection can have a name (shown on the canvas) and a rule: always (the default), when a formula is true, or otherwise (when no when connection from the same output was taken). A condition uses the routing scope: input, earlier nodes, Local vars, Project gv, Engine ev, trigger and now. The transition inspector builds a browsable Condition data tree from that same scope; clicking a field inserts its path. Its {x} shortcut inserts a Project or Engine property and it warns when a referenced Project property is absent; for example {input.amount} > {gv.LIMIT}. Branches that are not taken send skip tokens downstream, so merges never wait forever (dead-path elimination).

Waiting without holding anything

A step can return a wait instead of an output. The task becomes waiting with its wait details and costs nothing while it waits:

  • Approval: a person decides in the studio (Runs, Approvals) or through the API; the task resumes on approved or rejected.
  • Wait / timers: the task returns to pending with a not-before time.
  • Call Sutra: a child run starts; the parent task waits until the child finishes and receives what its Return step sent.
  • Replies across engines: a gateway caller waits on the engine that took the request even when another engine runs the reply step; the waiting engine polls the run row.

Errors, retries and the Error handler

Step settings give retries with a delay and a time limit. A failed attempt with retries left goes back to pending with a not-before time. When retries are spent, the step's error output is taken if it is connected; otherwise the Sutra's Error handler (an activity with no input) receives the error with the step name and message; otherwise the run fails. A failed run can be resubmitted: a new run starts with the same trigger input and the old run is marked resubmitted.

Test and debug runs

A test run uses the draft, not the deployed version. A debug run pauses before each step (paused tasks) and continues one step at a time, so input and output can be checked in the studio.

Data, mapping and expressions

Every step sees the same data: trigger (what started the run), input (the previous step's output), nodes.<Step name> (any earlier step), vars (Local variables), gv (Project properties), ev (Engine properties), secret (vault, server side only, masked in history), run, and inside loops item, index and iteration.

  • Templates (template.ts): {{input.name | upper}} inside text; a field that is only one template keeps the typed value (object, list, number).
  • Formulas (expr.ts): a value starting with =, such as =concat({input.first}, ' ', {input.last}). Parsed into a tree and evaluated by the engine; there is no eval.
  • Structured mapping (mapping.ts): the Activity Input tree from a shared schema or from paths, with For-Each on repeating nodes, where, group by, sort and conditions.
  • Shapes before running (design.ts, schemas.ts): each activity's output hint, schemas and earlier steps give the mapper a tree to drag from before any run exists.

Typed JSON/XML mapping (2.0.7)

Map JSON Data and Map XML Data are focused activity definitions over the same structured mapping engine as legacy Map data and Render JSON/XML. Mapping creates an object; rendering creates text. Existing generic activity identifiers remain valid.

Targets come from project-scoped JSON Schema/XSD references or a MappingValue containing path declarations, rules and optional typed definitions. Definitions carry scalar/object type, required/repeating flags, item bounds, description and object-element namespace URI. Attributes use @_name; list markers use [] in declarations and normalized paths in rules. XML has exactly one non-repeating element root. Namespace declarations become @_xmlns attributes on objects; qualified object names declare the corresponding prefix.

designSchemas and validateDoc use the same static checks: malformed formulas, unmapped required targets, invalid XML target names/root and contradictory cardinalities are errors; stale target rules and references absent from known source shapes are warnings. Hidden mapping fields in value-mode renderers are not checked. Output coercion retains legacy behavior unless typed definitions or a new typed activity opt into strict value checks. Type failures follow ordinary engine error routing.

Whole-result preview is a project-authorized, CSRF-protected POST endpoint. It resolves only the selected project's schema, evaluates expressions against supplied sample scope and serializes the result; it does not dispatch activities, write business data, call connectors, or create runs. Scope is capped at 256 KB and preview text at 1 MB. The editor debounces edits and discards stale replies, and labels the test-run source as possibly stale. Sample-to-schema inference is capped at 128 KB; XML DTD/entities are rejected. Generated XSD is a proposal and does not preserve source namespace bindings.

Instance validation is separate from mapping shape: schema-validation.ts reuses AJV for JSON Schema drafts 07/2019-09/2020-12 and xmllint-wasm (libxml2) for XSD 1.0. Runtime checks patterns, enums, ranges, conditional JSON rules and XML namespaces/order/choice/groups/cardinality even when the designer tree approximates them. XSD 1.1 is unsupported. Dependencies are preloaded from same-project XSD resources only; no network/host filesystem resolution. DTD/entities are rejected. Limits: 4 MB XML, 32 schema files / 1 MB schema text, four active validators / 64 waiting. Each WASM instance has a 32 MB linear-memory ceiling, excluding worker JavaScript overhead.

The shared boundary protects typed mapping, parse/render, Validate fields, structured local/FTP/SFTP files, outbound HTTP bodies/replies, received HTTP responses and opt-in REST/SOAP ingress. File reads validate JSON/XML only when strictValidation === true, a default-off checkbox shared by local/remote read, list and trigger fields; selecting a schema alone does not enable read validation. Strict reads require a matching JSON Schema/XSD. File writes with selected contracts are checked before creation/truncation; HTTP business requests before sending. Ordinary failures use engine error routing, Validate fields uses its invalid port, ingress rejects before run creation, and file triggers retain readError payloads. CSV streaming and schema-free behavior are unchanged. SOAP validates the namespace-preserved operation, not the full envelope or a prefix-stripped reconstruction. XML tree display is a separate bounded read-only view.

Certification evidence and exact executed checks are recorded in docs/benchmarks/release-2.0.7-verification.md. The functional mapping tests are not an industry certificate, XML standards-conformance claim, throughput benchmark or long-duration soak.

test/validation-samples.test.ts executes the bundled samples, checks every node description and schema reference, preserves edited schemas across reimport, exercises strict file-read on/off/missing/wrong-kind cases, and drives real local REST/SOAP listeners plus the sample HTTP client. Invalid ingress is checked against the durable run counter to prove that no run starts; invalid client data must not create a server run. The XML sample renders the normalized parsed object against its schema before revalidating XML text, restoring the declared namespace rather than guessing it from prefix-stripped data.

2.0.9 design integrity: shared Output, mapping and transition browsers derive observed fields from the explicit test session instead of projecting run values onto a different schema. Historical production outputs are not auto-loaded as samples; edits and schema reloads clear previews. Arrays show counts and complete small scalar lists. Activity sources and generated process documentation identify user names and activity types; documentation resolves named schema kinds/roots and connection kinds without resolving credentials.

POST /api/schemas/:id/impact requires Design permission on the schema's owning project. It analyzes a proposed definition using a request-local tree resolver injected into designSchemas; there is no temporary database update or process-global cache swap. The report compares shapes and new diagnostics for directly referencing saved drafts, not runtime compatibility, deployed snapshots or transitive schema dependencies. Both editors share a report UI with stale-response cancellation. npm run test:samples combines catalogue-wide static consistency checks with executable mapping and validation fixtures; real external-service gates remain separate.

Protected ingress verifies authentication and scopes before returning schema diagnostics. Authorized invalid requests receive REST 400 with error details or a SOAP Client fault; missing credentials return 401 and insufficient scopes 403 without schema details. Dedicated JWT-protected REST/SOAP tests verify the response distinctions and the unchanged durable run count.

2.0.10 strict boundaries and MongoDB M0

The optional activity validateStart hook runs before durable run creation. Manual start, REST, SOAP and WebSocket implement it so Test/Debug, Run API and direct engine calls cannot bypass their enabled ingress contracts. Execution validates again. contracts.ts centralizes project ownership, schema existence/kind, compilation and actual-value validation without coercion or sample substitution. SOAP object admission validates its namespace-aware XML representation with the real XSD backend.

Call Sutra validates input and, when configured to wait, its resumed child result. Return and internal channel activities have explicit strict controls. Local/remote file triggers reject invalid parsed events before downstream processing; a file-trigger failure can still have a failed run record. A selected descriptive schema with validation Off is not an enforcement promise. The schema-field inventory is a review gate, not proof of every activity's runtime behavior.

MongoDB metadata is separated from runtime resource lookup to avoid registry initialization cycles. The official driver uses a vault-backed URI, verified TLS, small resource-revision-keyed pools, operation budgets, abort signals and explicit shutdown. Public durable values use canonical Extended JSON rather than storing BSON instances or losing Int64/decimal precision. Cursor readers close in finally blocks and fail at the documented output ceiling rather than silently truncate.

The MongoDB palette exposes List Collections, insert, find/find-one/count/distinct, update/update-many/replace/upsert/find-one-and-update, delete and aggregation. Array filters select nested array members. A mapped collection-input override takes precedence over the General collection name; invalid overrides fail. Strict insert validates the complete batch before a write, but a later database error can leave partial writes. Update validation concerns the modifier/replacement request, not an inferred final document. Collection validators remain authoritative. Unrestricted commands, server JavaScript, durable change-stream/wait, transactions, GridFS and bulk activity implementations are not exposed.

Credential slots use a separate reference-resolution scope: Secret GV/EV properties provide their encrypted-vault reference, avoiding a second lookup of decrypted plaintext as a name. Normal runtime expressions retain secret-value semantics, with project and engine secret values registered for history masking. Get Properties excludes secret values. Inline entry is available in connection and Secret property editors; only references are stored in resource/project JSON, and existing permissions are unchanged. The eye reveals only freshly entered text; no stored-value reveal API is added.

Separate host/username/password and complete-URI modes coexist with legacy configurations. X.509 options use a client certificate/private key, optional private CA, verified TLS and $external; no user provisioning or automatic privilege grant occurs. Non-TLS is allowed only for direct loopback development. M0-baseline aggregation remains read-only/no-spill; General MongoDB requires explicit disk/output-stage flags and server authorization. X.509 and General-profile writes require separate live deployment certification, not an inference from password-based M0 tests.

Verification on 24 October 2026: 424 regression checks passed, 27 optional checks skipped; seven live Atlas M0 checks passed on MongoDB 8.0.34 with isolated seeded collections and cleanup. The local resolver refused SRV lookup, so live tests used a process-only alternate resolver; system DNS was unchanged. Driver-only transaction/change-stream/GridFS probes do not certify activities. Services: REST, SOAP and MCP

When a Sutra with a REST service, SOAP service or MCP skill trigger is deployed, rebuildRoutes resolves its General settings against the current Project and Engine properties, then adds its path to the gateway's route table on every engine. A request is matched (method and path with parameters, SOAP action, MCP endpoint), checked against the service's API policy, and starts a run of the deployed version with the request as trigger input. The gateway then waits for the run's reply step (HTTP response, SOAP reply, Reply to AI) up to SUTRA_REPLY_TIMEOUT_MS.

Gateway TLS and the ACME lifecycle

ACME is used only for the gateway's Let's Encrypt certificate mode. Its purpose is to prove control of the configured public names, obtain a browser-trusted certificate and replace it before expiry without an administrator copying certificate files. Self-signed and uploaded-certificate modes do not call ACME. SutraFlow supports the HTTP-01 challenge; wildcard certificates, which require DNS-01, are outside this path.

  1. Operator call. web/admin/Server.tsx first saves the TLS domains, contact email, staging choice and agreement through PUT /api/server/tls, then calls POST /api/server/tls/acme. The route requires the Server permission. api.ts switches the TLS mode to acme and starts requestAcme(reloadTls) without holding the HTTP request open for the whole issuance.
  2. Account and order. gateway/tls.ts takes the acme-certificate database lease, renewed while the order runs, so only one engine issues or renews the shared certificate. It decrypts the saved acmeAccountKey, or generates and encrypts one on first use, chooses the Let's Encrypt staging or production directory, and creates a fresh certificate private key and CSR containing all configured names. The maintained ACME client uses Node's native cryptography and @peculiar/x509; the removed node-forge compatibility export is neither installed nor called.
  3. HTTP-01 proof. For each authorisation the ACME client gives tls.ts a token and key authorisation. It is stored briefly in acme_challenges with the issuing engine and an expiry. Before normal gateway routing, every gateway.ts answers /.well-known/acme-challenge/<token> from that shared table. Public port 80 may therefore reach any healthy gateway node, but must reach the HTTP listener unchanged. The token is removed after validation and expired rows are cleaned before an order.
  4. Install. After Let's Encrypt validates every name, tls.ts saves the returned chain and matching private key through the encrypted settings store, records success or the error for the Admin Console, reloads its HTTPS context and raises the cluster generation. Every other engine reloads the shared certificate on its next heartbeat. Replacing the secure context does not deliberately drop existing connections.
  5. Renew. index.ts starts the renewal timer at boot. It checks after ten seconds and every twelve hours; in ACME mode, a missing certificate or one with fewer than 30 days left calls the same requestAcme(reloadTls) path. Failure leaves the current certificate in place and the next check retries.

The ACME account key and installed private key are encrypted with the server master key in shared settings. Challenge rows contain public key authorisations, not private keys, and expire after 15 minutes. An issuance lease expires if its engine disappears; an in-flight ACME order itself is not transferable, so a later request or renewal check starts a new order after the lease expires. The certificate expiry alert remains the operational backstop for failed renewal.

Apps, plans, firewall and the request log

Before routing, the gateway checks its firewall (deny wins; an allow list admits only its addresses). An API security policy with Gateway apps accepts an app's key (X-API-Key, or Authorization: Bearer sfk_...) or an access token from POST /oauth/token (OAuth2 client credentials, an hour, signed with a key kept in settings). The app must hold the scopes the policy requires; its plan is then counted in gw_usage in one transaction, so every engine of a cluster shares the count, and a full window answers 429 with Retry-After; answers carry X-RateLimit-* headers. Every request is written to gw_requests when it ends, for the Traffic page (timeline, p50/p95/p99, busiest and slowest services, apps) and the request log; housekeeping deletes entries after the chosen number of days. OpenAPI 3.1 is generated from the deployed REST services, their path parameters, body schemas and security, for the console and, when chosen, at /openapi.json on the gateway.

OAuth connections step by step

  1. The connection (resource kind oauthApp) holds the service, the client ID, the name of the vault secret with the client secret, and the scopes. A release carries it without any secret value or token.
  2. Start. GET /api/oauth/:id/start (permission Connections) returns the provider's authorization address with response_type=code, the scopes, the redirect address (<this server>/api/oauth/callback) and a state: the connection id, the redirect address, an expiry 10 minutes ahead and a random part, signed with HMAC-SHA256 under a key kept in settings (oauthStateKey). Provider extras are added: Google access_type=offline and prompt=consent (to get a refresh token), Dropbox token_access_type=offline, Twitch force_verify. A Microsoft connection with a tenant signs in at that tenant instead of common.
  3. Consent happens at the provider; SutraFlow never sees the password.
  4. Callback. GET /api/oauth/callback (open: the browser comes back from the provider) checks the state's signature and expiry, then posts the code, the redirect address, the client ID and the client secret (read from the vault at that moment) to the token endpoint.
  5. Storage. The access token and the refresh token are encrypted with the master key (AES-256-GCM, as vault secrets) and saved in settings under oauth:<connection id> with the expiry and scopes. All engines read the same row, so one sign-in serves the whole cluster; tokens never leave the server, and a different server signs in on its own.
  6. Use. Every call goes through accessToken(): a token with more than a minute left is used as it is; otherwise the refresh token is exchanged for a new access token (one refresh at a time per engine; the refresh token is kept when the provider does not send a new one) and saved. apiCall adds Authorization: Bearer; streamCall does the same for streamed uploads and downloads.
  7. Without a person. A connection can name a refresh token secret: on first use the server takes the refresh token from its vault (set by a pipeline) and signs in with it; sutra connect runs the start and waits for the callback from the command line.

Timers, listeners and channels

Triggers that are not requests are started by the leader engine:

  • Timers (scheduler.ts): cron expressions or intervals, with Project and Engine properties resolved when schedules are rebuilt.
  • Listeners (listeners.ts): folder watchers (File trigger), mailbox polling (Email trigger), queue and topic subscriptions (Service Bus), Drive and chat polling. General settings use the same property resolver as normal activities.
  • Broker acknowledgement and deduplication (connectors/bus.ts): auto mode lets the broker settle on receipt; client mode acknowledges only after run success; explicit mode records Confirm message's confirm, requeue or reject decision. Before starting a protected delivery it writes bus_messages with a reserved run id, keyed by Kafka topic/partition/offset or RabbitMQ/AMQP message id. A new leader that receives the same delivery consults that run: completed is acknowledged, failed/cancelled removes the reservation for retry, and an active/waiting RabbitMQ or AMQP copy is held without starting a duplicate while Kafka pauses that partition. A run that ends without an explicit decision follows the trigger's failure rule.
  • Broker protocols: Kafka uses KafkaJS and supports system or private CA trust, SASL plain/SCRAM and optional mutual TLS. RabbitMQ uses AMQP 0-9-1 over amqp or amqps. ActiveMQ/Artemis uses AMQP 1.0 over TCP or TLS. All three can use a private CA and an optional client certificate whose private key and passphrase remain vault secrets; certificate verification cannot be disabled. ActiveMQ resources use a container-id prefix and unique stable role suffixes, so publishers and listeners never contend for one client id. Java applications may use OpenWire/JMS against the same ActiveMQ destination; Classic needs transport.transformer=jms on its AMQP connector for body-level interoperability. Broker JVM/Erlang runtimes are server prerequisites, not SutraFlow client dependencies.
  • Channels (channels.ts): Send to channel starts every deployed Sutra of the project whose Channel trigger listens on that name. It reads deployments from the database, so it works the same on one engine or many.

When the leader stops or dies, another engine takes the lease and starts the timers and listeners itself. Kafka always supplies a stable offset identity; an external RabbitMQ or AMQP publisher must set a unique message id to receive the same duplicate-run protection. Requeue releases a delivery; reject asks the broker to dead-letter or discard it according to broker configuration. A configured delivery-count ceiling changes a requeue into reject. Broker delivery and outside activity effects remain at-least-once boundaries, so downstream idempotency keys are still required where an acknowledgement can be lost.

Storage

The default backend is SQLite built into Node (node:sqlite), in data/sutra.db, with WAL and a busy timeout. The administrative and low-frequency paths use q and tx in db.ts. With PostgreSQL those compatibility calls go through pgworker.ts, whose worker thread owns a connection while the caller waits on a SharedArrayBuffer.

The engine hot path is different: asyncdb.ts gives claim, complete, fail and settle truly asynchronous calls. On PostgreSQL it uses a main-thread pg.Pool, lets many independent runs have database work in flight, carries one pooled connection through each transaction, and discards a broken checked-out connection. SQLite and PGlite implement the same asynchronous interface over their existing connection. Advisory locks are keyed by run or queue operation, so transitions of one run are ordered while different runs proceed concurrently. The tests run the suite on SQLite and again on PGlite, with focused tests against a real PostgreSQL server.

Clusters: several engines

Engines that share one database form a cluster. No engine talks to another directly; the database is the only meeting point.

  • Work sharing. Every engine claims tasks with the atomic update above, so only one live claim owns a task at a time. A crash can make the activity execute again, so activities that call outside systems should use an idempotency key when the system supports one; the fenced database checkpoint itself applies once.
  • Heartbeat. Each engine updates its engines row every SUTRA_HEARTBEAT_MS with its active steps and draining flag. An engine silent for three beats is dead.
  • Leader. One engine holds the leader lease (renewed each beat, valid for three). It runs timers, listeners, recovery and housekeeping. If it stops renewing, another engine takes the lease.
  • Recovery. The leader puts tasks owned by dead engines back to pending. A new claim increases the task's claim number; a late completion from the former owner fails its fence and changes nothing.
  • Queue/topic takeover. Only the leader owns broker consumers. bus_messages binds a protected broker identity to its reserved run before that run starts. A replacement leader therefore follows the existing durable run instead of starting a duplicate. It acknowledges a completed run and clears a failed/cancelled reservation so retry can create a new run. An active/waiting duplicate is held unacknowledged on RabbitMQ/AMQP with an extra delivery slot; Kafka pauses only that partition and checks again. Settlement still occurs only at the configured on-receipt, run-success or explicit-confirmation boundary.
  • Deploy propagation. A deploy, connection or project change raises a generation number in settings; every engine compares it on each beat and reloads its routes (and the leader its timers and listeners).
  • Locks. The leases table also gives short cluster-wide locks, such as the deploy-folder lock so replicas starting together deploy a package once.
  • Studio in a cluster. A studio with SUTRA_WORKERS=0 edits and deploys; the engines run.

Leader failure, switch and return

  1. Normal operation. The leader renews the database lease on every beat. Only it owns timers, folder/mailbox/Drive/broker listeners, orphan recovery, run promotion, alerts and housekeeping. All engines can serve gateway requests and execute claimed tasks.
  2. Failure detection. If the process, host or network path disappears, it cannot renew the lease or heartbeat. Existing database rows do not disappear. After three heartbeat intervals the lease is eligible for takeover and the engine is considered dead.
  3. Takeover. Exactly one eligible engine updates the lease. Its becameLeader hook rebuilds timers and listeners and begins one-only maintenance. It resets running tasks owned by dead engines to pending; the next owner gets a higher claim number. Folder-trigger checkpoints in file_listener_state and file_listener_files let the new leader distinguish the first baseline from files that arrived, changed or failed under the old leader.
  4. Former leader returns. On its next successful heartbeat it reads and tries to renew the authoritative lease. If another engine owns a valid lease, its lostLeader hook stops timers and listeners. It remains a normal engine: its gateway can serve requests and its worker slots can claim ordinary tasks, but it does not run leader-only work. It may lead again only after the current lease is released or expires and it wins a later database update.

What happens during other failures

  • Activity error or timeout. The executor aborts at the limit. The task retries after its configured delay, routes through its connected error output, invokes the Sutra Error handler, or fails the run in that order.
  • Engine dies while an activity runs. Its uncommitted transition is absent. The leader requeues the task after the heartbeat threshold; the activity can run again, while fencing prevents the old claim from committing later.
  • PostgreSQL is unavailable. No engine can safely claim, start or checkpoint durable work. Heartbeat errors are contained rather than terminating the process; broken pool clients are discarded, the notification listener reconnects, and periodic polling resumes from the durable queue after the database returns. A process keeps its last local leader state while the answer is unknown, but it cannot acquire or prove a new lease without PostgreSQL.
  • Notification is lost. Nothing is lost from the queue. The next periodic poll sees the pending row.
  • Graceful drain. Readiness turns off and leadership is released immediately. Current steps get the drain window; unfinished claims return to pending for another engine.

The guarantee is durable at-least-once activity execution with exactly-once fenced state transitions, not exactly-once effects in an outside system. This is why request IDs, object keys or other idempotency controls should be passed to external APIs for non-repeatable operations.

Releases and deployment

Project packages

A release is a project package (packages.ts): a JSON file with format sutraflow-package v1 holding every deployed Sutra at its version, the project's connections (secret names, never values), shared schemas and WSDLs, Project properties and logging, a manifest and a sha256 checksum. The manifest includes Sutras, secrets, activity types and each Memory table's key, database/driver, referenced source objects, queries, schedule/time zone, limits and failsafe. Preflight rejects missing Memory-table dependencies and invalid configuration before deployment.

  • Check: the server knows every activity type, the secrets exist in its vault, and API paths and MCP skill names are not used by another project.
  • Deploy: Sutras are matched by name and created or updated as new versions (unchanged documents are left alone); Sutras not in the package are undeployed unless kept. Each deployment is stored in package_deployments with its report.
  • Roll back: deploys the package before the latest one, or a chosen one from history.
  • Test: deploys into a throw-away server and runs the package's Sutras.
  • Import: a new project from chosen Sutras of a package, as drafts by default (no address clashes, missing secrets only warn), not recorded as a deployment. Copy builds a package of chosen Sutras of a project on the same server and imports it the same way.

With SUTRA_MODE=engine the designer is not served and its API is closed. The console (web/admin, server/src/console.ts) is for what is deployed. Start and stop

Start order

  1. Open storage and create missing tables.
  2. Register every activity; connect the variable hooks; load deployment config files.
  3. Deploy packages from SUTRA_DEPLOY_DIR under the deploy-folder lock (skipped when the checksum is already deployed). A package that fails stops the start.
  4. Start the engine worker slots and the cluster beat; the leader starts timers and listeners.
  5. Build the gateway routes, start the gateway listeners and certificate renewal.
  6. Start the admin API. /ready now answers 200.

Graceful stop

On SIGTERM, Ctrl+C or POST /api/engine/drain: readiness turns off so load balancers stop sending requests; the engine leaves leadership and stops timers and listeners; running steps get up to SUTRA_DRAIN_MS to finish, and the rest go back to pending for another engine; the gateway closes after its waiting callers have their replies; database and bus pools close; traces are flushed.

Alerts

The cluster leader checks every enabled rule every six heartbeats (30 seconds by default), so a cluster alerts once however many engines it has. A check reads the database: failed or slow runs in a window, the gateway request log for error rate and p95 latency, engine heartbeats, pending steps older than a limit, waiting approvals, the gateway certificate, and the listeners of the leader. When a rule's condition holds and it has no open alert, an alert opens and every channel of the rule is told; while it holds, the alert is updated and, unless acknowledged, a reminder goes out every chosen number of minutes; when it clears, the alert resolves and the channels are told if the rule says so. Deliveries are recorded on the alert with their result. Channels: email through an SMTP connection; a webhook with a JSON body (event, text, alert) signed with an HMAC of a vault secret in X-Sutra-Signature; or a deployed Sutra started with the alert as its input. Resolved alerts are deleted after SUTRA_AUDIT_RETENTION_DAYS. sutra alerts exits with 1 while a critical alert is firing, for scripts and monitors.

Security

  • Studio: the first visit creates the administrator; signed session cookies that end when the account is disabled or signed out everywhere; changing requests need the X-Sutra header; the admin port listens on 127.0.0.1 unless set otherwise.
  • Accounts and roles: people and system accounts hold roles (Administrator, Developer, Deployer, Operator, Approver, Viewer, API caller, or custom ones) for all projects or one project. Every admin API route checks a permission for its project (guard.ts); lists show only the caller's projects. Five wrong passwords lock an account for 15 minutes; an administrator-set password must be changed at the next sign-in; at least one active administrator always remains.
  • Automation: SUTRA_ADMIN_TOKEN acts as an administrator, compared in constant time. System accounts get their own API tokens (stored as hashes, with expiry) limited to their roles; headless engines accept only tokens.
  • Audit: every change, sign-in and refused request is recorded with who, when, from where and the result, searchable and exportable as CSV.
  • Vault: AES-256-GCM; values never leave the server through the API; masked in run history and logs.
  • Gateway: per-service API policies (API key, Basic with listed users or system accounts holding Call services on the project, JWT, mutual TLS, WS-Security); TLS with uploaded or Let's Encrypt certificates.
  • Outbound: security profiles, client certificates, OAuth tokens stored encrypted, circuit breakers on HTTP connections.
  • Data never becomes code: SQL text, transactions and procedure names may resolve only administrator-managed Project/Engine properties; input, trigger, earlier-output and Local-variable references there are rejected and runtime values must use bound parameters. Formulas and templates are parsed, not evaluated; scripts receive values as environment variables and a JSON file; programs get arguments without a shell; file activities stay inside their folder; custom JavaScript runs in a sandboxed worker with limits.
  • SSO client binding: OpenID Connect uses PKCE, state and nonce. SAML uses a one-time request in the shared database plus a short-lived signed client cookie; the callback must present both. A browserless client follows the same contract by retaining the cookie returned by the start request and sending it with the SAML callback.
  • Policies off by default: scripts and release activities each need an administrator's switch in Admin Console → Server → Runtime. Project and Engine properties are always read-only to Sutras.
  • Vendor supply chain: every build checks reviewed local dependency trees and packaging scope; connected CI, releases and a weekly workflow compare them with npm. A newer upstream version must be reviewed for API and behavior changes and pass focused plus complete regression tests before its pinned baseline moves.

Benchmark scope and reproducibility

The runs above are functional and fault-handling certification. They did not measure sustained messages/second, end-to-end p50/p95/p99, maximum queue depth, TLS CPU cost or long-duration broker-outage recovery. The earlier engine soak figures elsewhere in the documentation are not messaging-protocol benchmarks. A messaging performance result must state broker/client versions, partitions or prefetch/credit, payload size, acknowledgement mode, durability, TLS/authentication, engine count, database/network topology and duration alongside throughput, latency, errors, redeliveries and duplicates.

Reproduce native coverage with test/kafka.test.ts, test/rabbitmq.test.ts and test/activemq.test.ts; enable their opt-in environment variables and supply credentials through the test environment. REST coverage is test/broker-rest.test.ts. test/connectors.test.ts covers guard and TLS configuration failures. The Java OpenWire and TLS proxy fixtures live under test/fixtures and are test-only. Certificates, passwords and keys are not included in source, sample packages or this report.
